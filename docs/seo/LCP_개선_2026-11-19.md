## 무엇이 느렸나 (측정으로 확인한 것)

수정 전 로컬 측정에서, 방 그림이 **0.88초에야 요청되고 3.18초에 도착**했습니다. 이유:

1. **그림을 늦게 알아챔.** 방 배경은 `app.css` 안의 `background-image` 라서, 브라우저가 CSS 를 다 받은 뒤(약 0.9초)에야 받기 시작합니다.
2. **글꼴이 그림보다 먼저 대역폭을 가져감.** 크롬은 글꼴을 가장 높은 우선순위(VeryHigh)로 받습니다. 첫 화면 글자에 필요한 글꼴 조각이 14개(약 210 KB)라 0.9초부터 한꺼번에 받으면서 그림(High)을 밀어냈습니다. 그림은 글꼴이 다 끝난 뒤에야 속도를 냈습니다.
3. **첫 화면에 안 보이는 썸네일 5개(약 78 KB)** 도 같은 시간에 받았습니다(공간 고르기 팝업 안의 그림).
4. **`core.js`·`i18n.js` 가 첫 그리기를 막음.** 둘 다 `<head>` 의 동기 스크립트라 다 받고 실행해야 화면이 그려졌습니다(`i18n.js` 는 압축 전 119 KB).
5. (참고) 점검 문서 ⑥절 의 "Google Fonts 외부 1건"은 2026-11-17 글꼴 자체 호스팅 이후로는 사실이 아닙니다. 지금은 `fonts.css` 가 자기 서버의 `fonts/` 를 가리킵니다.

## 남은 문제

**1) 느린 망 첫 방문의 레이아웃 이동(CLS).** 이번 측정(느린 4G 실제 제한)에서 수정 전 0.45 ~ 0.56, 수정 후 0.34 ~ 0.42 로 둘 다 기준(0.1 이하)에 못 미칩니다. 원인은 이번 수정과 무관한, 앱 구조의 문제입니다:

- 첫 화면의 정적 HTML 과 `app.js` 가 채우는 화면이 다릅니다: ① 상태 줄(`#statusbar`) 6칸은 이모지만 있고 글자는 `app.js` 가 채워서 높이가 226 → 256 px 로 늘고, ② 소개 글 `#lead` 의 둘째 문장이 HTML 은 짧은 옛 문구, `i18n.js` 는 긴 문구라 3줄 → 4줄(59 → 78 px)이 됩니다. 이 때문에 아래 방 그림이 약 49 px 밀립니다. (정적 HTML 과 `i18n.js` 한국어가 다른 곳은 소개 글 외에도 있습니다: `snd.btn`, `demo.sub`, `next`, `log.empty`, `bk.note`, `foot.feedback`, `foot.u5`, `foot.u6`, `snd.apply`.)
- `app.js` 가 첫 그리기보다 늦게 실행될 때(느린 망)만 보입니다. 빠른 망에서는 `app.js` 가 먼저 실행돼 이동이 0 입니다(네트워크·CPU 제한 없이 측정: 수정 전·후 모두 이동 없음). 그래서 PageSpeed(11-11 측정 CLS 0)에는 안 나타납니다.
- 영어·독일어 브라우저는 2026-11-19 에 병합된 "Read in English?" 안내 줄(PR #33)이 `app.js` 실행 때 맨 위에 생기면서 같은 이동이 하나 더 있습니다(en-US 가 ko-KR 보다 0.08 ~ 0.11 큰 이유로 보임).
- 고치려면 화면 문구·높이를 정하는 결정이 필요해서 이번 PR 에 넣지 않았습니다. 후보: (a) 정적 HTML 의 한국어를 `i18n.js` 와 같게 맞추고 상태 줄 칸에 최소 높이를 줌(디자인 소폭 변경), (b) 첫 그리기를 `app.js` 실행 뒤로 미룸(FCP 가 약 1초 늦어짐), (c) 안내 줄을 자리 확보 후 표시. 대표님이 정해 주시면 별도 작업으로.

**2) LCP 는 로컬에서 기준을 넘었지만 라이브는 배포 뒤 확인 필요.** 로컬은 서버 왕복 시간이 거의 0 이라 라이브보다 0.17초 빠르게 나옵니다(수정 전 비교). 그 만큼을 더해도 2초 안팎(추정)입니다. PageSpeed 웹 화면의 숫자는 모의 제한 방식이라 이 문서와 다를 수 있습니다.

그 밖에 남은 것(이번엔 하지 않음): `i18n.js`(압축 전 119 KB, 세 언어 한 파일)의 언어별 분리 — 첫 로드 약 80 KB 감소하지만 LCP 에는 이제 영향이 작습니다. 글꼴 조각 14개(약 210 KB)를 쓰는 글자만 담은 더 작은 글꼴로 만드는 것(빌드 작업).
